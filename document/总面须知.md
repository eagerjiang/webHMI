## 一、先明确：总经理究竟在判断什么

从工业领域总经理的视角，这次面试的核心问题不是“你会不会 Vue”，而是：

> 把一个客户的设备需求交给你之后，你能不能在合理时间内，做出美观、可靠、能部署、能联调、客户愿意使用的 Web HMI，并且不制造新的安全和交付风险？

总经理通常会从以下八个维度判断候选人：

| 判断维度 | 总经理真正关心的问题 | 应证明的内容 |
| --- | --- | --- |
| 行业理解 | 是否知道工业前端与互联网前端的区别 | 懂设备状态、报警、参数、权限、互锁、数据质量和现场环境 |
| 产品能力 | 是否只会照设计稿开发 | 能从操作员任务出发重新组织信息和交互 |
| 视觉审美 | 做出的界面能否代表公司见客户 | 有层级、有一致性、有工业可读性，不为炫技牺牲效率 |
| 独立交付 | 小团队是否可以放心把模块交给你 | 能拆需求、定边界、做实现、测试、文档和演示 |
| 工程质量 | Demo 能否走向真实项目 | 考虑异常、断线、权限、审计、性能、部署和回滚 |
| 协作能力 | 能否和控制、现场、客户、总部一起解决问题 | 不甩锅，能用事实复现问题并推动闭环 |
| 投入产出 | 招你之后能否降低交付成本 | 会复用组件、沉淀模板、利用 AI 提效并对结果负责 |
| 稳定性与动机 | 为什么离开井松、空窗为什么较长、现在能否稳定投入 | 原因真实简洁，影响稳定工作的因素已经解决，方向选择清晰 |

### 1.1 总经理希望看到的信号

- 先讲用户、场景和业务价值，再讲技术。
- 能明确说出当前 Demo 的边界，不把模拟控制包装成真实设备控制。
- 知道工业软件的“正常路径”不难，真正难的是异常路径和恢复路径。
- 能把美观解释为信息层级、状态识别、操作效率和错误预防，而不只是配色。
- 知道什么事情必须向控制侧或现场工程师确认，不盲目替业务做决定。
- 有 30/60/90 天的落地思路，而不是只说“我会努力学习”。
- 对 AI 的态度是积极使用、严格验证、保护数据、责任不外包。

### 1.2 容易失分的信号

- 把岗位说成普通 Vue 前端，只关注组件、CSS 和接口。
- 演示时不停介绍按钮，却说不清操作员为什么需要它。
- 为了显得懂工业而编造 PLC、SCADA、InfluxDB 或现场项目经验。
- 遇到未知问题立刻回答“这个让后端处理”“这个让产品决定”。
- 只说界面“科技感强”，说不清警告、停机、确认、复位的差别。
- 强调 AI 写了多少代码，却不能解释、修改和验证代码。
- 回答职业规划时只谈职位、薪资或尽快带团队。

### 1.3 早期上海团队会额外判断什么

成熟公司的前端岗位可以依靠产品、测试、运维和固定流程分工；早期中国团队更可能要求一个人跨越需求、设计、开发、联调和客户沟通。总经理会特别观察：

| 关注点 | 建议证据 |
| --- | --- |
| 能否在信息不完整时推进 | 先列假设、风险和待确认项，快速做低成本原型 |
| 是否只适合被分配清晰任务 | 讲一个自己澄清需求、推动闭环的井松案例 |
| 能否与奥地利总部协作 | 用事实、日志、最小复现和书面结论减少时差沟通 |
| 能否兼顾产品与客户项目 | 共性沉淀为组件/配置，客户差异通过扩展点控制 |
| 空窗后能否稳定投入 | 原因可信、影响因素已解决、有现实到岗和长期计划 |
| 是否会无限承诺 | 能接受合理出差和现场，但会确认频率、资源与支持机制 |

推荐表态：

> 我理解早期团队的岗位边界会比成熟公司更宽，我可以在合理范围内承担需求澄清、界面设计、开发、联调和文档。但对于 PLC 控制、安全互锁、客户验收责任等专业边界，我会与对应负责人共同确认，不会用个人承诺代替团队能力。

## 三、把招聘要求翻译成总经理语言

招聘要求不是七条孤立技能，而是一条完整交付链：

```text
理解设备和操作员任务
→ 设计 Web HMI
→ 接入状态、参数、报警和时序数据
→ 完成交互与业务逻辑
→ 配合控制侧和现场侧部署验证
→ 处理版本联动和故障
→ 用 AI 和工程化方式提高后续交付效率
```

### 3.1 岗位要求与当前 Demo 的对应证据

| 招聘要求 | 当前项目中的证据 | 面试时的表达重点 |
| --- | --- | --- |
| Web HMI 与工业应用开发 | Vue 3、Canvas 2D、整机页、锁定标记页 | 不是静态稿，状态和交互由模拟数据持续驱动 |
| 设备操作与状态展示 | 放卷、10 个 PU、收卷、车速和单元状态 | 操作员先看整线，再定位异常单元 |
| 参数和报警反馈 | PU 参数、报警抽屉、确认/恢复/复位/启动 | 明确报警生命周期，避免把“确认”误当成“消除故障” |
| 时序数据呈现 | 1200 点信号、500ms 帧、参考线和检测窗 | 理解刷新、冻结、断线、最后有效帧和数据质量 |
| 工业应用层数据组织 | 整机快照、信号帧、状态中心、派生数据 | 组件不各自维护业务真相，状态和规则集中管理 |
| 现场部署与排查 | 当前尚未接真实设备 | 主动说明产品化所需的适配、日志、重连、部署和回滚 |
| AI 辅助开发 | 可说明实际使用流程 | 强调验证、测试、责任边界和敏感数据保护 |
| 美观与交互 | 16:9 重构、固定 2.5D、工业暗色设计 | 美观服务于识别效率、操作稳定和客户产品形象 |

### 3.2 必须主动承认的边界

以下边界要主动、平静地说明，不要等面试官揭穿：

- 当前是前端模拟数据，没有接 PLC、真实 InfluxDB 或后端服务。
- 速度、启动和版辊偏移只修改浏览器内状态，不能控制真实机械。
- 当前检测窗只保存在浏览器会话中，不是正式配方或生产数据库。
- 当前权限、审计、报警历史、断线重连和版本回滚仍属于产品化范围。

推荐话术：

> 我把这次实操作为产品原型和前端架构验证，而不是伪装成已量产的软件。它已经验证了界面结构、状态流、曲线交互和报警闭环；真实接入时，我会把模拟数据源替换成明确的数据适配层，并补齐权限、审计、互锁、数据质量、部署和回滚能力。

这不是示弱，而是在证明工程判断力。

### 3.3 招聘要求中 Demo 没有完整覆盖的部分

总经理可能专门追问未展示的内容。不要临时发挥，按下表准备边界和思路：

| JD 内容 | 当前状态 | 应如何回答 |
| --- | --- | --- |
| 参数页面与配方 | Demo 只有局部参数交互 | 正式产品需要草稿、校验、权限、下发回执、版本和审计 |
| 权限控制 | 未实现完整 RBAC | 前端控制可见性，可信服务端再次鉴权；重要操作二次确认 |
| 订单、产量、OEE | 未实现业务页面 | 先统一订单边界、计划时间、停机分类、良品和节拍口径，再做看板 |
| InfluxDB 查询 | 当前为实时模拟帧 | 说明 measurement/tag/field、时间范围、聚合、降采样和保留策略需要后端共同设计；不声称已有实战 |
| 现场部署和版本联动 | 未接真实环境 | 准备日志、健康检查、配置备份、版本兼容、维护窗口和回滚思路 |
| 自然语言查数/智能助手 | 当前未做产品功能 | AI 只做辅助解释或查询，控制指令必须有权限、约束、确认和审计 |

#### 参数下发的标准状态链

```text
读取当前值
→ 用户编辑草稿
→ 类型/范围/工艺条件校验
→ 权限与必要的二次确认
→ 提交命令
→ 等待设备回执
→ 成功后更新正式值并审计
→ 失败则保留原值、提示原因并允许重试
```

#### 订单、产量和 OEE 的最低认识

> 看板开发的难点通常不是图表，而是口径。订单开始和结束如何定义、计划停机是否计入、短停怎么归类、良品由哪个系统确认、理论速度如何获得，这些不统一，前端算出的 OEE 再漂亮也不可信。我的做法是先让业务、设备和数据侧确认口径、时间边界与数据责任，再实现查询和展示。

## 四、90 秒自我介绍模板

将方括号替换成自己的真实经历，不能编造。

> 您好，我叫[姓名]。2018 年至 2021 年，我在上海奕盛有限公司从事 .NET 后端开发，积累了接口、数据和业务逻辑方面的基础；2021 年 5 月进入井松智能后转为前端开发，主要负责工业项目页面的修改和迭代，并参与过 3D 数字孪生工厂的可视化展示。这段经历让我从数据和业务逻辑进一步走到用户界面与工业场景，也让我认识到工业前端不仅是页面呈现，还要考虑信息是否清楚、数据如何映射到设备场景，以及长期维护和客户使用。
>

#### 4.6.6A 浏览器端心跳检测怎么做

先明确协议边界：浏览器 JavaScript 使用的 `WebSocket` API 不能直接构造协议层 Ping 帧。协议层 Ping/Pong 通常由浏览器和服务器底层处理，前端业务代码无法监听或发送。因此业务前端常与服务端约定应用层消息：

```json
// 前端定时发送
{ "type": "ping", "timestamp": 1724300000000 }

// 服务端收到后返回
{ "type": "pong", "timestamp": 1724300000000 }
```

基本流程：

```text
WebSocket open
→ 记录 lastAliveAt
→ 启动心跳定时器
→ 定时发送 ping
→ 收到 pong 或正常业务消息，更新 lastAliveAt
→ 超过 heartbeatTimeout 仍无任何消息
→ 主动 close 当前连接
→ 由 onclose 统一进入重连流程
```

为什么“正常业务消息”也可以更新 `lastAliveAt`：只要能够持续收到服务端数据，就能证明连接仍然存活；没有业务数据时，再依靠 `ping/pong` 验证。具体以服务端协议为准。

推荐参数仅作为示例，不能脱离服务端配置照搬：

```text
heartbeatInterval：10 秒发送一次 ping
heartbeatTimeout：25 秒没有任何服务端消息则判定失活
```

`heartbeatTimeout` 应大于发送间隔，并为网络延迟和浏览器定时器误差留余量。浏览器后台标签页可能节流定时器，工业项目还要结合 kiosk/前台运行方式与 `visibilitychange` 做验证，避免误判。

#### 4.6.6B 断线重连怎么做

不能在 `onerror`、`onclose`、心跳超时三个地方各自创建新连接，否则可能同时启动多个 WebSocket。统一原则是：

```text
onerror：只记录错误，等待连接关闭
onclose：唯一的重连调度入口
心跳超时：只负责 close，让 onclose 接管重连
```

重连状态机：

```text
IDLE
→ CONNECTING
→ OPEN
→ 心跳超时 / 网络中断 / 服务端关闭
→ RECONNECT_WAIT
→ CONNECTING
→ OPEN

用户主动离开页面
→ STOPPED（清理所有定时器，不再重连）
```

重连间隔不要固定为 1 秒无限请求。使用指数退避和随机抖动：

```text
第 1 次：约 1 秒
第 2 次：约 2 秒
第 3 次：约 4 秒
第 4 次：约 8 秒
……
最大约 30 秒，并叠加少量随机时间
```

随机抖动可以避免大量客户页面在服务端恢复时同时发起连接。鉴权失败、权限不足或参数错误等不可恢复错误不应无限重连，应提示用户并等待重新登录或人工处理。

#### 4.6.6C 可练习的 TypeScript 实现

下面代码用于掌握完整结构，消息类型、订阅内容、关闭码和鉴权方式必须按真实服务端协议调整。

```ts
type SocketState =
  | 'idle'
  | 'connecting'
  | 'open'
  | 'reconnect-wait'
  | 'stopped'

interface SocketOptions {
  heartbeatIntervalMs?: number
  heartbeatTimeoutMs?: number
  reconnectBaseMs?: number
  reconnectMaxMs?: number
}

export class ResilientWebSocket {
  private socket: WebSocket | null = null
  private heartbeatTimer: number | null = null
  private reconnectTimer: number | null = null
  private reconnectAttempts = 0
  private lastAliveAt = 0
  private stopped = true
  private state: SocketState = 'idle'

  constructor(
    private readonly createUrl: () => string,
    private readonly onData: (message: unknown) => void,
    private readonly onStateChange: (state: SocketState) => void,
    private readonly options: SocketOptions = {},
  ) {}

  start() {
    if (!this.stopped) return
    this.stopped = false
    this.connect()
  }

  stop() {
    this.stopped = true
    this.clearHeartbeat()
    this.clearReconnectTimer()

    const current = this.socket
    this.socket = null
    current?.close(1000, 'page destroyed')
    this.setState('stopped')
  }

  send(message: unknown): boolean {
    if (this.socket?.readyState !== WebSocket.OPEN) return false
    this.socket.send(JSON.stringify(message))
    return true
  }

  private connect() {
    if (this.stopped) return
    if (
      this.socket?.readyState === WebSocket.CONNECTING ||
      this.socket?.readyState === WebSocket.OPEN
    ) {
      return
    }

    this.setState('connecting')
    const socket = new WebSocket(this.createUrl())
    this.socket = socket

    socket.onopen = () => {
      if (socket !== this.socket) return

      this.reconnectAttempts = 0
      this.lastAliveAt = Date.now()
      this.setState('open')
      this.startHeartbeat()

      // 按真实协议重新订阅，并请求当前完整快照。
      this.send({ type: 'subscribe', topics: ['device-position', 'goods-position'] })
      this.send({ type: 'snapshot-request' })
    }

    socket.onmessage = (event) => {
      if (socket !== this.socket) return

      // pong 或正常业务消息都能证明连接仍然存活。
      this.lastAliveAt = Date.now()

      let message: unknown
      try {
        message = JSON.parse(event.data)
      } catch {
        return
      }

      if (
        typeof message === 'object' &&
        message !== null &&
        'type' in message &&
        message.type === 'pong'
      ) {
        return
      }

      this.onData(message)
    }

    socket.onerror = () => {
      // 这里只记录日志；由 onclose 统一调度重连，避免重复连接。
    }

    socket.onclose = (event) => {
      if (socket !== this.socket) return

      this.socket = null
      this.clearHeartbeat()

      if (this.stopped) return

      // 示例：鉴权失败/禁止访问时停止自动重连。
      if (event.code === 4001 || event.code === 4003) {
        this.stopped = true
        this.setState('stopped')
        return
      }

      this.scheduleReconnect()
    }
  }

  private startHeartbeat() {
    this.clearHeartbeat()

    const interval = this.options.heartbeatIntervalMs ?? 10_000
    const timeout = this.options.heartbeatTimeoutMs ?? 25_000

    this.heartbeatTimer = window.setInterval(() => {
      const socket = this.socket
      if (socket?.readyState !== WebSocket.OPEN) return

      if (Date.now() - this.lastAliveAt > timeout) {
        // 4000 是应用自定义关闭码示例。
        socket.close(4000, 'heartbeat timeout')
        return
      }

      socket.send(JSON.stringify({ type: 'ping', timestamp: Date.now() }))
    }, interval)
  }

  private scheduleReconnect() {
    if (this.stopped || this.reconnectTimer !== null) return

    const base = this.options.reconnectBaseMs ?? 1_000
    const max = this.options.reconnectMaxMs ?? 30_000
    const exponential = Math.min(base * 2 ** this.reconnectAttempts, max)
    const jitter = Math.floor(Math.random() * 500)

    this.reconnectAttempts += 1
    this.setState('reconnect-wait')
    this.reconnectTimer = window.setTimeout(() => {
      this.reconnectTimer = null
      this.connect()
    }, exponential + jitter)
  }

  private clearHeartbeat() {
    if (this.heartbeatTimer === null) return
    window.clearInterval(this.heartbeatTimer)
    this.heartbeatTimer = null
  }

  private clearReconnectTimer() {
    if (this.reconnectTimer === null) return
    window.clearTimeout(this.reconnectTimer)
    this.reconnectTimer = null
  }

  private setState(state: SocketState) {
    this.state = state
    this.onStateChange(state)
  }
}
```

不要逐字背代码，必须能解释以下六个设计点：

1. 为什么心跳超时只 `close`，由 `onclose` 统一重连；
2. 为什么需要 `stopped` 区分主动关闭和异常断开；
3. 为什么只能保留一个重连定时器；
4. 为什么使用指数退避和随机抖动；
5. 为什么重连成功后要重新订阅并请求快照；
6. 为什么组件销毁时必须清理心跳、重连、订阅和 WebSocket。

#### 4.6.6D 重连成功不等于数据已经恢复

工业位置数据在断线期间仍可能持续变化。重新连接后如果只继续接收增量消息，页面可能永远缺少断线期间的关键状态。因此顺序应是：

```text
WebSocket 重连成功
→ 重新鉴权（若协议需要）
→ 恢复设备/货物主题订阅
→ 请求当前完整快照或最新版本
→ 用快照校准本地状态
→ 再继续处理实时增量消息
→ 页面从“同步中”切换为“实时”
```

若消息带序列号或时间戳，可丢弃旧消息、识别缺口；若没有，则至少用最新快照建立可信基线。控制命令在连接中断、重连等待和快照同步期间应禁止或安全降级。

#### 4.6.6E HMI 页面如何显示连接状态

| 连接状态 | 页面表达 | 控制策略 |
| --- | --- | --- |
| connecting | 正在连接，显示加载状态 | 禁止控制 |
| open + 数据正常 | 实时，显示最后更新时间 | 按权限和互锁开放 |
| reconnect-wait | 连接中断，正在重试第 N 次 | 禁止控制，旧值标记为过期 |
| open + snapshot sync | 已连接，正在同步最新状态 | 暂不允许关键控制 |
| stopped/auth failed | 连接停止或登录失效 | 明确提示重新登录/人工处理 |

不能让旧位置继续以正常颜色移动，也不能把“WebSocket 已 open”直接显示成“设备数据已恢复”。连接、订阅、快照和数据新鲜度是不同层次。

#### 4.6.6F 必须完成的测试清单

- 正常连接后定时发送 ping，收到 pong 不触发重连；
- 服务端不回 pong，超过超时后关闭并进入重连；
- 服务端主动关闭，只有一个重连定时器；
- 关闭网络再恢复，间隔按退避策略变化，最终恢复；
- 服务端重启后重新订阅并请求完整位置快照；
- 连续失败不会每秒无限轰炸服务端；
- 用户离开页面后不再心跳、不再重连；
- 多次进入退出页面不会出现多个并行连接；
- 重连等待时旧设备/货物位置显示为过期，控制按钮禁用；
- 鉴权失败不无限重试；
- 重连后旧序列/旧时间的数据不会覆盖最新状态；
- 浏览器标签页进入后台再恢复时不出现心跳误判或重复连接。

#### 4.6.6G 60 秒面试回答

> 浏览器端 WebSocket 通常要和服务端约定应用层心跳，因为 JavaScript 不能直接构造协议层 Ping 帧。连接成功后，前端定时发送 ping，并记录最后一次收到 pong 或正常业务消息的时间；超过阈值仍没有响应，就主动关闭连接，让 onclose 作为唯一入口调度重连，避免多个回调重复创建连接。重连采用指数退避和随机抖动，用户主动离开页面时则停止心跳和重连。
>
> 对工业 HMI 来说，连接重新 open 还不够。还需要重新鉴权和订阅，请求设备与货物的最新完整快照，校准断线期间的状态后，页面才能从“同步中”恢复为“实时”。连接中断和同步期间要把旧数据标成过期，并禁止关键控制。

真实经历边界的补充：

> 井松项目使用过 WebSocket 接收设备和货物位置，但完整断线重连不是我当时实现的。这是我针对自身短板近期补做和掌握的方案，我可以讲清状态机、代码结构和测试方法，但不会把它倒推成过去已经落地的经历。

#### 4.6.7 路径动画和实时状态如何同步？

> 路径动画不能只依赖“每帧移动固定距离”，否则不同电脑帧率下速度会不同。更合理的是根据时间增量、业务进度或设备状态计算当前位置；路径可以由离散点或曲线描述，动画状态要区分运行、暂停、完成和异常。收到新数据时，需要判断是平滑过渡、立即校正还是停止等待，不能让画面动画与真实业务状态长期偏离。

本项目已知数据中包含运动物体和货物的实时位置，因此可以从真实经历出发回答：

> WebSocket 会持续返回运动物体和货物的位置，前端把新的位置映射到对应 Three.js 对象。为了避免画面跳动，需要结合当时真实实现说明是直接更新位置，还是在旧位置与新位置之间做插值；这两种不能混说。如果当时只是直接更新，就如实说，并补充现在会评估插值和平滑策略。

准备说明自己实际使用的是：

- 离散路径点还是 Three.js 曲线；
- 使用时间增量还是接口进度；
- 如何处理暂停、恢复、跳点和路径切换；
- 动画是业务真实状态还是演示效果。

#### 4.6.8 页面切换后内存持续增长怎么处理？

> Three.js 对象从 scene 中移除，并不等于 GPU 资源已经释放。页面销毁或模型重载时，需要停止 `requestAnimationFrame`，移除窗口、鼠标和控制器事件，取消数据订阅，并遍历释放 geometry、material 和 texture；必要时再释放 controls、render target 和 renderer，同时清除对象引用。之后通过多次进入退出页面观察内存是否仍持续增长。

推荐记忆顺序：

```text
停动画循环
→ 移除事件和数据订阅
→ 从场景移除对象
→ dispose geometry/material/texture
→ 释放控制器、渲染目标和 renderer
→ 清理引用
→ 重复进出页面验证内存曲线
```

若当时只处理了其中一部分，就说“当时采用了哪些措施；现在复盘认为还应补哪些”，不要把完整清单都说成实际代码。

#### 4.6.9 如何判断卡顿来自哪里？

> 我会先复现并固定测试场景，然后分层排查：Network 看资源下载；Performance 看主线程脚本、模型解析和长任务；渲染统计看 draw call、三角面和帧率；Memory 看多次操作后对象是否持续增长；再暂时关闭动画、数据更新、阴影或部分模型做对比实验。通过逐层隔离确定瓶颈，而不是看到卡顿就笼统说模型太大。

```text
下载慢：网络和资源体积
解析慢：模型结构、纹理和主线程长任务
GPU 慢：draw call、面数、阴影、透明和像素比
业务慢：高频全量遍历、重复计算、过多 DOM 标签
越用越慢：事件、动画循环、订阅或 GPU 资源未释放
```

#### 4.6.10 不同浏览器和电脑性能差异如何处理？

> 首先明确公司支持的浏览器和最低硬件，不追求所有环境效果完全一致。启动时可以检测 WebGL 能力和关键特性，根据设备性能限制像素比、阴影、后处理、标签数量和模型细节；窗口变化时正确更新相机比例和 renderer 尺寸。对不支持或性能不足的环境提供明确提示或降级展示，同时在目标工控机和客户浏览器上完成实际验证。

可选降级项：

- 限制 `devicePixelRatio`；
- 关闭或降低阴影、抗锯齿和后处理；
- 降低模型细节、纹理尺寸和同时显示的标签；
- 减少动画频率或非关键动态效果；
- 低性能环境切换到简化 3D 或 2D 总览。

本项目另一个可以确认的设计是**按观察距离控制信息细节**：

> 工厂场景范围较大，远处即使显示全部细节也看不清，反而增加信息和渲染负担。因此远距离主要保留整体位置和轮廓，用户靠近或聚焦某一区域后，再显示更清楚的设备或货架信息。这是一种距离分级展示思路。除非当时确实使用了 `THREE.LOD`，否则不要直接说使用了 Three.js 的 LOD 类。

#### 4.6.11 3D 项目解决了什么业务问题？为什么不用 2D？

> 3D 的价值不是更炫，而是让用户理解工厂空间布局、设备分布、物流路径或跨区域关系。普通 2D 页面更适合参数设置、报警处理和高频操作；3D 更适合全局态势、空间定位、路径展示和对外演示。因此项目中应该让 3D 承担它擅长的空间表达，再通过详情面板或 2D 页面处理精确数据和操作。

如果项目最终主要用于展示、投标或展厅，就如实说明，不要强行包装为操作员生产控制系统。

### 5.3 演示中必须讲出的五个设计取舍

#### 取舍一：为什么不用自由旋转 3D

> 工业操作员需要稳定的空间记忆。固定视角的参数化 2.5D 能保持放卷、PU 和收卷位置不变，加载和交互成本也更低。这里追求的是快速识别，不是展示模型技术。

#### 取舍二：为什么不能只依赖颜色

> 运行、警告、停机除了颜色，还用状态点、文字、边框和报警符号共同表达，避免色觉差异、屏幕偏色或现场光照导致误判。

#### 取舍三：为什么单击 PU 不直接跳页

> 单击先建立当前设备上下文并打开详情，操作员仍然能看到整线位置；只有通过明确入口才进入锁定标记，降低触摸屏误触和上下文丢失。

#### 取舍四：为什么检测窗有草稿和应用状态

> 操作员调整过程不应立即覆盖正在参与计算的正式窗口。草稿可以预览、取消，确认应用后才影响计算，这相当于一个小型事务。

#### 取舍五：为什么冻结显示但不停止采集

> 冻结用于稳定观察某一帧，不应影响后台数据接收。显示帧与最新采集帧分离，可以同时满足观察和持续计算。

### 5.4 美观问题的标准回答

> 我理解工业产品的美观不是装饰，而是秩序感和可信度。这个界面用暗色降低长时间观看的视觉刺激，用青色标识可操作内容，用绿、黄、红表达运行、警告和停机；通过字号、间距、分组和留白建立层级。更重要的是，同一种状态在不同页面保持一致，同一种操作有一致的反馈。最终仍需要和真实操作员做可用性测试，因为设计师认为清楚，不等于现场人员一定操作高效。

### 5.5 演示结束的 30 秒总结

> 当前版本已经验证了两类核心界面、持续数据刷新、检测窗坐标、信号异常和报警生命周期。若进入真实项目，我下一步不会继续堆页面，而是先确定平台数据模型和控制边界，由 Edge 或后端适配 OPC UA 等设备协议，前端通过平台提供的 WebSocket/REST 接口获取数据，再增加数据质量、权限、审计、互锁和设备回执，通过 Edge 部署、日志和版本回滚形成可交付闭环。

## 六、需要掌握的一分钟技术说明

总经理未必会深入代码，但会观察能否用简单语言讲清复杂系统。

### 6.1 整机状态链

```text
mockMachineSource 生成整机与 PU 快照
→ hmi store 统一管理状态、报警和业务操作
→ Vue 页面与 MachineCanvas 负责展示和交互
```

表达：

> 组件不自己维护设备业务真相，整机、报警和操作状态集中在状态中心，后续替换真实数据源时不会要求所有页面重写。

### 6.2 信号链

```text
mockSignalSource 生成/接收每帧 1200 点
→ latestFrame 始终保存最新采集帧
→ displayedFrame 保存当前显示帧
→ SignalCanvas 根据当前视口绘制曲线和检测窗
```

表达：

> 最新采集数据和屏幕显示数据分开，所以冻结画面时仍可以继续采集，恢复后也能立即回到最新状态。

### 6.3 检测窗坐标

必须能脱离代码讲出：

```text
屏幕坐标
→ 减去 Canvas 在页面中的偏移
→ 减去绘图区边距
→ 按当前 viewport 比例换算成数据坐标
```

关键句：

> 检测窗保存的是数据坐标，不是屏幕像素，因此缩放、平移或改变屏幕尺寸后不会漂移。

### 6.4 报警生命周期

```text
报警发生
→ 操作员确认
→ 故障条件恢复
→ 停机报警复位
→ 人工启动
```

关键句：

> 确认只表示“人已经看到”，不等于故障消失；复位只解除锁存，也不应自动启动设备。

### 6.5 总经理面必须会画的产品架构

总经理未必检查具体代码，但可能通过架构追问判断：当前 Demo 能否接入真实设备、出现异常怎么定位、未来能否低成本复制给不同客户。应能在纸上 3 分钟画出以下参考链路，并在 5–10 分钟内解释清楚。它是合理的分层方案，不代表 UBIQUE 已确认采用完全相同的接口，真实实现以公司平台为准。

```text
PLC / 设备
    ↓
协议与数据适配层（OPC UA / Modbus / MQTT 等）
    ↓
UBIQUE Edge / 后端服务
    ↓
REST：配置、历史数据
WebSocket：实时状态、曲线、报警
    ↓
前端数据适配层
    ↓
状态管理
    ↓
Vue 页面 + Canvas 实时绘制
```

推荐说明：

> 当前 Demo 使用模拟数据，但页面不应该长期与某个模拟源或 PLC 地址耦合。真实产品中，应通过 Edge 或后端适配层统一设备协议，转换成包含设备对象、标签、时间戳和质量码的稳定数据模型。前端通过 REST 获取配置和历史数据，通过 WebSocket 接收实时状态、曲线和报警。这样设备协议或客户现场变化时，HMI 页面不需要整体重写。

控制命令必须是带校验和回执的反向链路：

```text
操作员点击
→ 前端权限和状态判断
→ 必要时二次确认
→ 后端权限与参数校验
→ 控制服务
→ PLC / 设备执行
→ 返回设备回执
→ 页面更新状态
→ 写入操作审计
```

必须说出的边界：

> 浏览器不能把“按钮点了”直接当成“设备执行成功”。前端只能表示命令已发出、等待回执、执行成功或执行失败，真实结果必须以控制侧和设备回执为准。前端按钮禁用也只是用户体验，权限、参数约束和设备互锁必须在可信的服务端或控制侧再次执行。

### 6.6 当前 Demo 的模块架构怎么讲

> 当前项目采用 Vue 3 组织页面与组件，集中管理整机、信号和报警状态；整机与实时曲线使用 Canvas 绘制，模拟数据源与页面逻辑分离。页面不直接生成业务数据，而是通过数据源层接收帧，再由状态层派生设备状态，最后交给 Vue 和 Canvas 展示。将来接入真实接口时，核心思路是替换数据适配层，而不是大规模重写页面。

回答不能停在“使用了 Vue、Vite 和 Canvas”，还要说明模块边界、数据如何流动、为什么这样设计，以及真实数据接入时改动发生在哪里。

### 6.7 高频架构问题与回答要点

#### 为什么使用 Canvas，不用 ECharts 或 SVG？

> 本题不只是展示曲线，还需要在曲线上创建、拖动和缩放检测窗，并准确完成屏幕坐标与数据坐标换算。Canvas 在绘制层级、命中区域和交互控制方面更直接。真实项目中不会一律坚持 Canvas：标准趋势图可以评估成熟图表库；复杂实时交互和高频自定义绘制更适合 Canvas；大量可单独操作的矢量对象再评估 SVG。

#### 1200 点每 500 毫秒刷新如何保证性能？

- 不为每个点创建 DOM 元素，使用 Canvas 批量绘制；
- 区分实时采集帧与当前显示帧，冻结画面不停止后台采集；
- 数据或交互变化时才安排重绘，避免无意义更新；
- 正确清理定时器、订阅和事件监听，防止长时间运行后泄漏；
- 数据量继续增加时，评估滑动窗口、降采样、分层绘制和 Web Worker；
- 使用帧率、CPU、内存和长时间运行测试判断，而不是夸大 1200 点本身的压力。

#### 为什么区分“最新数据”和“当前显示数据”？

> 冻结曲线只应该冻结操作员看到的画面，不能停止后台采集。否则恢复显示时会丢失中间状态，也容易让用户误以为设备或采集已经停止。因此最新帧持续更新，显示帧在冻结时保持不变；解除冻结后，再明确同步到最新数据。

#### 网络中断和数据过期如何处理？

```text
正常
→ 延迟升高
→ 数据过期
→ 连接中断
→ 自动重连
→ 重新同步快照/缺失数据
→ 恢复正常
```

页面要显示最后更新时间与连接状态；旧值不能继续伪装为实时值；连接或设备状态不可信时，控制命令应禁止或安全降级；断线、重连和命令失败要进入可检索日志。

#### 如何从模拟数据接入真实 PLC？

若没有直接完成过 PLC 接入，不得说成已有经验：

> 我不会让浏览器分别直连不同型号的 PLC。更合理的是通过 Edge 或后端协议适配层统一设备协议，把地址、寄存器或节点转换为平台可理解的设备对象、标签、时间戳和质量码，前端只依赖稳定的数据模型。当前实现验证的是前端数据边界和交互；具体协议与 UBIQUE 平台接入方式需要入职后在测试环境跑通。

#### 如何支持不同客户的定制？

> 核心原则是把稳定部分做成产品能力，把变化部分做成配置。设备对象、报警模型、权限、实时数据和命令状态属于平台共性；客户品牌、页面布局、标签映射、阈值和部分流程可以配置。无法配置的差异通过明确扩展点或模块实现，避免为每个客户复制一套代码形成长期分支。

#### 如何部署、升级和回滚？

> 工业现场可能网络受限、停机窗口短、版本不能随意变化。产品化后需要考虑 Edge 侧部署、版本固定、配置备份、健康检查、日志导出、维护窗口升级和可验证回滚。升级前还要检查数据模型、配置和接口兼容性，不能只替换前端文件就算完成。

#### 安全架构最低要考虑什么？

- RBAC 权限、登录和会话管理；
- TLS 通信、参数范围与业务状态校验；
- 重要操作二次确认、控制侧互锁和设备回执；
- 操作、报警和版本变更审计；
- 客户数据隔离、依赖漏洞与版本管理；
- 不随意向外部 AI 服务上传客户代码、设备数据和商业信息。

## 七、工业领域痛点及回答角度

### 7.1 供应商锁定与硬件停产

总经理关注：客户为什么愿意买 UBIQUE？

> 传统自动化把 PLC、HMI、运动控制和硬件平台绑定较深。硬件停产或供应链变化时，客户可能被迫做大规模迁移。开放、硬件相对独立的平台可以提高软件复用率，减少最后一次采购、库存和重新验证成本。

### 7.2 IT 与 OT 的冲突

> IT 希望快速迭代、开放组件和云端协作；OT 更重视确定性、安全、连续运行和长生命周期。好的工业平台不是简单把互联网技术搬进工厂，而是让开放开发方式服从设备安全和生产连续性。

### 7.3 存量设备和协议碎片化

> 客户现场不会因为采用新平台就立刻替换所有 PLC、驱动和设备。真实落地必须支持渐进式接入，在控制或 Edge 侧对 OPC UA、Modbus、EtherCAT、MQTT 或私有接口建立适配边界，并向应用层明确时间戳、数据质量和命令回执；前端不直接承担所有工业协议接入。

### 7.4 网络安全和 CRA

> 工业设备生命周期可能超过十年，安全不能只靠上线前测试，还需要软件物料清单、漏洞管理、补丁、权限、审计和安全更新。欧盟 CRA 的报告义务将从 2026 年 9 月 11 日适用，主要义务从 2027 年 12 月 11 日适用。对出口欧洲的中国设备厂商，这可能是现实的采购驱动力。

### 7.5 时序数据与 OEE

> InfluxDB 解决的是时序数据存储和查询问题，不会自动解决业务语义。OEE 还需要统一计划生产时间、停机分类、良品、性能速度和订单边界。前端不能只画漂亮图表，而要确认数据口径、时间范围、缺失值、异常值和聚合方式。

### 7.6 工业 AI 的边界

> AI 可以用于自然语言查数、文档问答、报警辅助解释、代码和测试，但不能未经校验直接生成设备控制指令。涉及控制时必须有权限、参数约束、设备互锁、人工确认和审计，也不能随意把客户代码与设备数据发送给外部模型。

## 八、高概率问题及回答框架

### 8.1 为什么选择我们，而不是普通互联网前端岗位？

> 我在 2018 年至 2021 年做过 .NET 后端，2021 年进入井松后转向工业前端，做过工业页面修改和 3D 数字孪生工厂展示，所以我不是因为这次招聘才临时选择工业方向。现在希望把后端阶段的数据和接口理解、井松阶段的工业可视化经验连接起来，进一步聚焦 Web HMI、工业数据和平台型产品。UBIQUE 不只是做一个项目页面，而是把实时控制、Edge、Web HMI 和生命周期能力做成平台，这与我下一阶段想积累的能力比较一致。

### 8.2 你认为这个岗位最难的是什么？

> 最难的不是 Vue 页面，而是建立可信的数据和操作边界。页面显示的状态是否最新、断线后如何表达、报警和复位如何处理、命令是否获得设备回执，这些会直接影响客户信任。另一个难点是标准平台与客户定制之间的平衡，需要把共同需求沉淀为可复用模块。

### 8.3 如果客户说“界面不够好看”，你怎么处理？

> 先确认“不好看”背后的具体问题：品牌风格、信息过密、操作路径、对比度还是与原系统差异太大。然后结合操作员任务做两到三个低成本方案，用真实数据和典型任务评审，而不是只围绕个人审美争论。工业界面最终要同时满足品牌、效率和安全。

### 8.4 如果控制工程师说是前端问题，而前端认为数据不对，怎么办？

> 先建立同一条证据链：设备原始值、平台时间戳、接口报文、前端接收日志和页面显示值。使用同一工单、同一设备、同一时间复现，判断是数据源、传输、映射、状态派生还是渲染问题。先把问题定位并恢复交付，再讨论责任和预防措施。

### 8.5 如何把当前 Demo 变成真实产品？

先用一句话回答，再根据追问展开第六章：

> 我会先跑通一条可信的真实数据与控制链路，再补齐异常、安全、部署和运维能力，最后沉淀成可复用平台模块，而不是继续堆页面。

展开顺序：

1. 定义设备对象、标签、时间戳、质量码和命令模型；
2. 用适配层替换模拟数据源；
3. 引入断线重连、最后有效值和数据质量；
4. 增加 RBAC、操作审计、二次确认、互锁和设备回执；
5. 接入 InfluxDB 查询、降采样、保留策略与业务口径；
6. 增加 Docker/Edge 部署、健康检查、日志、版本升级和回滚；
7. 完成组件测试、集成测试、长时间运行和现场验收。

### 8.6 为什么使用 Canvas，而不是直接使用图表库？

> 题目不仅要求实时曲线，还要求创建、拖动和缩放检测窗，并完成屏幕坐标与数据坐标换算，所以我选择 Canvas 直接控制绘制和命中区域。真实项目中会根据交互复杂度、维护成本和团队能力重新评估，标准趋势图不排斥成熟图表库。详细取舍见第 6.7 节。

### 8.7 你没有真实 PLC/InfluxDB 项目经验，如何胜任？

若确实没有，必须诚实：

> 我不会把这次模拟项目说成真实 PLC 或 InfluxDB 项目，但我也不是完全没有工业背景。我在井松担任前端开发，做过工业项目页面修改和 3D 数字孪生工厂展示，熟悉把工业场景和设备信息转化为前端可视化。我的已有经验主要在应用展示层，不会把它包装成控制侧经验。对于还没有直接做过的平台能力，我会先在测试环境跑通数据模型和查询方式，再跟控制及现场人员完成一条真实链路，并沉淀接口、日志和验收清单。

### 8.8 你如何保证进度？

> 先把需求拆为必须交付、可延后和待验证三类；尽早用原型确认信息结构和操作流程；对设备接口、数据口径和现场条件提前列风险；每个阶段都提供可运行版本。出现风险时不等到截止日前才报告，而是同时给出影响、替代方案和需要的决策。

### 8.9 你如何使用 AI？

> 我把 AI 用于方案比较、代码骨架、测试补充、文档和重复性重构，但先给出业务约束，再审查异常路径和工业语义，最后通过测试和人工评审确认。涉及客户代码、设备数据和商业信息时遵守公司的工具白名单与数据政策。AI 可以提高速度，但交付责任仍然在我。

### 8.10 你的缺点是什么？

选择真实但可改进的内容，不能回答“过于追求完美”。示例：

> 我过去在井松积累了工业前端和 3D 可视化经验，但在[真实短板，例如 PLC 协议、InfluxDB、海外平台协作或完整 Web HMI 产品负责人经验]方面还不够深入。为减少这个差距，我在这次项目中刻意补充了报警生命周期、断线、数据质量和控制边界的设计。进入岗位后，我会优先跑通一条完整真实链路，尽快把已有工业可视化经验转化为优贝克平台上的交付能力。

### 8.11 你能接受出差和现场支持吗？

根据真实接受程度回答，不要为了拿 Offer 无条件承诺：

> 合理、提前规划的项目出差和现场联调我可以接受，因为工业软件必须理解真实设备和操作员。但我也希望了解常规频率、单次周期、紧急支持机制以及现场和研发之间如何轮值。

### 8.12 如果需求频繁变化怎么办？

> 先判断变化来自客户认知逐步清晰、平台能力限制，还是缺少决策人。把稳定的数据和业务模型与容易变化的页面配置分开；通过原型、验收标准和变更记录减少反复；对影响范围和工期透明沟通，而不是表面答应后在交付末期集中暴露。

### 8.13 为什么我们应该录用你？

> 我能同时提供三类价值：早期后端经历形成的接口和数据边界意识、井松阶段的工业页面与 3D 数字孪生展示经验，以及把复杂状态独立做成可演示成果的执行力。当前 Demo 不只是完成页面，还对状态链、异常恢复、报警和操作边界做了系统处理。我不会把没有做过的 PLC 或平台经验包装成做过，也不会把自己包装成当前成熟的全栈工程师，但能用前后端视角更顺畅地参与 Web HMI 和工业数据应用协作。

### 8.14 如果入职后发现平台和预期不同怎么办？

> 我会先理解平台当前阶段、客户承诺和团队目标，再区分短期项目需求与长期产品方向。对确实存在的问题，我会带着复现、影响和可行方案沟通，而不是只做评价。早期团队一定有不完善，我关注的是目标是否清楚、决策是否有效、问题是否能被推动解决。

### 8.15 你的职业规划是什么？

> 一到两年内，我希望成为能独立负责 Web HMI 和工业应用交付的工程师，不只做界面，还能处理数据模型、部署和现场问题。三到五年希望承担 Web HMI 产品模块或设计系统的技术负责人，推动组件复用、工程质量和用户体验。当前第一目标不是尽快转管理，而是建立对产品和交付真正负责的能力。

### 8.16 为什么离开井松智能？

只能使用真实原因，建议采用“事实—现状—方向”三段式，不评价老东家，不展开私人细节。

> 我在 2024 年 3 月离开井松，主要原因是[真实、可验证的原因]。这件事情当时确实影响了我连续工作的安排，但目前[相关因素]已经解决，我现在可以稳定投入工作。这段经历也让我更明确，下一阶段希望继续留在工业领域，并把方向聚焦到 Web HMI、工业数据和平台产品。

不要说：

- 井松项目低端、管理混乱或发展不好；
- 我就是累了，什么都不想干；
- 空窗太久，所以现在什么工作都可以；

### 8.17 空窗两年多，你做了什么？为什么现在才回来？

> 这段时间我主要[真实说明：处理个人事项/学习/项目/求职节奏等]。我承认这段空窗比较长，所以公司关注我的稳定性和当前能力是合理的。现在影响稳定工作的因素已经解决；这次 Web HMI 实操是我用可运行成果证明当前状态的方式。代码、设计取舍和测试都可以现场展开，我希望用现在能交付什么，而不是只靠过去公司经历来证明自己。

回答控制在 60–90 秒，不为每个月编故事。总经理最终关心的是三件事：原因是否可信、问题是否解决、现在能否持续稳定工作。

### 8.18 为什么不回井松，为什么选择优贝克？

> 我认可井松给我的工业前端和 3D 数字孪生展示经验，也不会否定上一家公司。两家公司的业务形态不同：井松更偏智能仓储、移动机器人和系统集成项目；优贝克更聚焦开放式机器自动化平台、Web HMI、Edge 和工业数据。我的选择不是判断谁更高级，而是希望从工业页面和场景展示进一步深入设备状态、参数、报警、时序数据和平台产品，同时参与中国团队早期建设和国际协作。

### 8.19 请讲三个井松项目案例

使用第 4.4 节已经填写完成的证据表。每个案例按“情境—本人任务—关键行动—结果—复盘”回答，控制在 2–3 分钟；不要把团队成果全部算到自己身上。

### 8.20 井松智能与优贝克有什么差别？

面试时使用业务形态和个人方向做比较，不评价谁更高级，也不要主动讨论井松的利润、管理或负面信息：

> 井松是业务和交付体系相对成熟的智能物流系统企业，项目更聚焦智能仓储、移动机器人、WMS/WCS 和智能工厂交付，我在那里积累了工业页面和 3D 工厂可视化经验。优贝克背靠 TTTech，业务更聚焦开放式机器自动化平台、Web HMI、Edge 和工业数据，中国团队也处于较早阶段。两家公司方向不同；我选择优贝克，是因为下一阶段希望在 Web HMI 和平台产品方向形成更深能力，并参与本地团队与总部的协作建设。

自己判断机会时可以认识到：井松的组织和业务确定性更强；优贝克的个人影响空间更大，但客户阶段、团队资源和职责边界需要通过反问确认。这部分用于个人决策，不要原样对总经理说“贵公司风险更高”。

### 8.21 你如何与奥地利总部协作？

> 跨国协作最怕信息只存在口头和聊天记录里。我会把问题整理成最小复现、版本与环境、期望和实际结果、日志或截图、影响范围和需要对方决策的事项；同步后形成书面结论，明确负责人和截止时间。时差下尽量减少来回询问。对于术语和需求歧义，先用原型、接口样例和验收标准对齐，而不是等开发完成后再解释。

若英语口语不是强项，不必声称“完全无障碍”，可以如实说明技术文档、邮件或会议的实际水平，并给出准备和确认机制。

> 先判断需求是中国市场共性、单一客户差异，还是现有平台能力不足。共性需求应以产品提案和证据推动总部纳入路线图；客户差异优先通过配置、扩展点或隔离模块实现；影响核心架构和安全边界的修改不能为了短期验收直接分叉。若交付时间不允许等待总部版本，就明确临时方案、维护成本、退出计划和责任人。

### 8.23 为什么从后端转前端？以后还会再转吗？

必须结合真实原因回答，不能只说“前端更有意思”。推荐结构：

> 我在 2018 年至 2021 年于上海奕盛从事 .NET 后端开发，积累了接口、数据模型和业务逻辑基础。2021 年 5 月进入井松时转为前端开发，之后持续做到 2024 年 3 月，工作内容也从页面迭代延伸到 3D 数字孪生工厂展示。[这里补充当时转岗的真实原因]。这不是频繁换方向，而是从数据和逻辑走到工业应用与用户交互。现在我的主方向仍然是 Web HMI 和工业前端；后端经历的价值是帮助我理解接口、数据质量和系统边界，不是说入职后又要改做后端。

如果早期后端技术已经较久没有使用，应诚实说“有基础和理解能力”，不要声称可以立即独立负责现代后端生产系统。

**你的最低接受是多少？**

**上一份工资是多少？**

> 我在井松 2024 年 3 月离职前的税前固定月薪是 14K，另外是[按真实情况填写薪资月数和奖金]。那是基于当时岗位职责和公司的薪酬体系。这次岗位的公开范围是 18–25K，职责和能力要求也不同，所以我当前期望是 20K 左右，也愿意结合整体总包沟通。

若 HR 追问“14K 到 20K 涨幅是否太高”：

**现在有没有其他 Offer？**

如实回答。可以说在接触其他机会或尚无正式 Offer，但不要制造虚假截止日期施压。

### 10.3 必须确认的条件

- 12、13 还是 14 薪；

不要在总经理面开场主动追问全部福利。先完成业务交流，在对方明确推进意向后再确认薪酬结构。

- 对出差、加班、汇报关系和验收责任表述模糊；
- 所有产品决定都要总部批准，但又要求中国团队快速定制；
- 把 AI 当作压缩人员配置的主要手段，却没有数据和质量规范。

## 十二、面试当天的表达方法

### 12.1 回答结构

优先使用以下结构，避免散乱：

```text
先给结论
→ 说明依据或场景
→ 提供一个真实例子
→ 说明边界或下一步
```

示例：

> 我会选择固定 2.5D，而不是自由 3D。因为操作员需要稳定的设备位置，固定视角识别更快，也降低触摸误操作和渲染成本。在当前 Demo 中，放卷、10 个 PU 和收卷始终按工艺顺序排列。后续如果客户确实需要维修拆解或空间定位，再针对特定任务引入 3D，而不是为了视觉效果全面 3D 化。

### 12.2 遇到不会的问题

禁止凭感觉编造。推荐说法：

> 这个具体平台细节我目前没有真实项目经验。我先说我会如何确认：第一核对数据源和接口语义，第二确认控制与权限边界，第三在测试环境验证正常和异常路径。如果您愿意，我也可以结合现有经验给出一个初步方案，但不会把它当作已经验证的结论。

### 12.3 与总经理讨论不同意见

- 先确认对方目标，不急着反驳方案；
- 用客户任务、风险、时间和成本比较方案；
- 提供两个可选路径，不只指出问题；
- 被否定后能继续推进，不争输赢；
- 涉及安全、合规和真实设备风险时，要坚持明确记录和验证。

### 12.4 面试状态

- 回答控制在 30–90 秒，复杂题最长约 2 分钟；
- 总经理打断时立即停下来听，不抢话；
- 少用“肯定、绝对、完全没问题”；
- 多使用“当前阶段、基于现有信息、我会先验证”；
- 不贬低传统工控界面、竞品或上一家公司；
- 不主动炫耀使用了多少 AI；
- 说“我负责验证和交付”，不要说“AI 帮我做完”。

### 12.5 面试结束的 30 秒收尾

如果总经理问“还有什么补充”，不要重新讲一遍简历：

> 今天交流后，我对这个岗位的理解更清楚了。我的优势是井松阶段的工业页面和 3D 工厂可视化经验、Web HMI 的设计与开发能力，以及这次实操证明的当前状态；PLC、InfluxDB 和贵公司具体平台能力中我没有做过的部分，我会诚实补齐。如果双方匹配，我愿意在入职前 30 天先跑通平台和一条真实数据链路，尽快形成可验收结果。谢谢您今天的时间。

### 12.6 跨国环境的最低英文准备

招聘要求未明确要求英文面试，不需要临时背长篇英文自我介绍，但至少应能看懂或说出以下项目词汇：

| 中文 | 英文表达 |
| --- | --- |
| 实时控制 | real-time control |
| 边缘计算/边缘部署 | edge computing / edge deployment |
| 时序数据库 | time-series database |
| 数据质量码 | data quality code |
| 报警确认 | alarm acknowledgment |
| 设备回执/命令回执 | device feedback / command acknowledgment |
| 断线重连 | reconnection after disconnection |
| 权限与操作审计 | access control and operation audit |
| 版本升级和回滚 | version upgrade and rollback |

若临时切换英文，先用短句讲事实，不为了流利而增加未经验证的内容；没听清时直接请求对方重复或确认理解。

### 心跳与重连两天专项计划

目标不是背出全部代码，而是能画状态机、解释关键设计、手写核心逻辑并说清工业数据恢复。

#### 第一天：理解并能写出主流程（约 2.5 小时）

1. **30 分钟**：不看文档写出心跳与重连的区别，特别记住浏览器不能直接发送协议层 Ping；
2. **30 分钟**：手画 `CONNECTING → OPEN → RECONNECT_WAIT → OPEN`，再补充主动 `STOPPED`；
3. **60 分钟**：不复制粘贴，自己重新输入第 4.6.6C 的类；每个回调旁写一句职责；
4. **30 分钟**：逐条解释为什么只从 `onclose` 调度重连、为什么指数退避、为什么销毁时停止；
5. **30 分钟**：把井松真实经历与近期学习分成两列，防止面试时混说。

第一天完成标准：

- 60 秒讲清心跳与重连区别；
- 3 分钟画出状态机；
- 不看文档写出 `onopen/onmessage/onclose/startHeartbeat/scheduleReconnect/stop` 的伪代码；
- 明确说出井松当时没有做完整断线重连。

#### 第二天：异常测试与面试表达（约 2.5 小时）

1. **45 分钟**：按第 4.6.6F 逐项推演正常、无 pong、网络中断、服务端重启、鉴权失败和页面销毁；
2. **45 分钟**：若有可用测试服务，实际关闭网络或服务观察状态；没有服务时，用假时钟/模拟回调手工验证“只能有一个重连定时器”；
3. **30 分钟**：重点练“重连 open 后为何必须重新订阅和请求快照”；
4. **30 分钟**：连续录制三遍第 4.6.6G 的 60 秒回答；
5. **15 分钟**：接受追问——退避、抖动、旧数据、后台标签页、主动关闭分别怎么处理；
6. **15 分钟**：只复习一页关键词，不再临时增加复杂方案。

第二天完成标准：

- 能指出代码中防重复连接、防页面销毁后继续重连的条件；
- 能解释“WebSocket open 不等于业务数据已可信”；
- 能说出重连后的“鉴权—订阅—快照—增量”顺序；
- 能把近期补做与井松真实经历清楚分开。
