# 云平台须知

> 适用场景：将融合实时控制、Edge、Web HMI、设备数据、软件生命周期和网络安全的工业自动化产品逐步扩展为云平台。
>
> 核心原则：工业产品上云不是简单地把前端构建产物部署到云服务器，而是建设“现场实时控制、Edge 边缘自治、云端统一管理”的混合架构。

## 1. 先明确“上云”的含义

在开始技术选型之前，需要先和产品、控制、交付、安全及法务团队确认以下问题：

1. 云端只提供监控和数据分析，还是允许远程控制设备？
2. 产品形态是公有云 SaaS、客户私有化部署，还是两者都要支持？
3. 现场断网后，本地 HMI 和设备是否必须继续正常工作？
4. 中国区的账号、日志或设备数据是否会传给境外总部？
5. 预计有多少客户、工厂、设备和采集点？
6. 数据采样频率是多少，原始数据需要保存多久？
7. 客户现场是否允许设备访问公网，网络和防火墙有哪些限制？
8. 设备通过 OPC UA、Modbus、MQTT 还是现有 Edge API 接入？
9. 系统可接受的延迟、停机时间和数据丢失量是多少？
10. 总部现有平台已经提供哪些设备管理、身份认证、升级和安全能力？

对工业自动化平台，推荐的默认形态是：

> 本地完成实时控制，Edge 负责设备接入和现场自治，云端负责跨设备管理、数据服务、运维和软件生命周期，本地与云端分别提供适合各自场景的 HMI。

## 2. 推荐总体架构

```text
工厂现场
┌─────────────────────────────────────────┐
│ PLC / 运动控制 / 安全控制               │
│   └── 毫秒级控制、互锁、急停，永不上云  │
│                     ↓                   │
│ Edge 网关 / 工业 PC                     │
│   ├── OPC UA / Modbus 等协议适配         │
│   ├── 数据标准化、质量码、时间戳         │
│   ├── 断网缓存、恢复补传、日志           │
│   ├── 本地 Web HMI，断网仍可使用         │
│   └── 设备证书，通过 TLS 主动连接云端    │
└──────────────────┬──────────────────────┘
                   │ MQTT / HTTPS
                   │ 原则上由现场主动向外连接
                   ↓
云平台
┌─────────────────────────────────────────┐
│ IoT/MQTT 接入 → 数据处理 → 时序数据库   │
│                                         │
│ 设备管理   报警服务   历史趋势           │
│ 用户/租户  权限审计   OTA/版本管理        │
│ 命令服务   API/BFF    日志监控            │
└──────────────────┬──────────────────────┘
                   ↓
          Web 门户 / 移动端 / 开放 API
```

### 2.1 必须明确的架构边界

- 浏览器不能直接连接 PLC，也不应直接解析各种工业协议。
- 公有云不能承担 EtherCAT、运动控制、急停等实时闭环控制。
- 现场断网不能导致设备停机或本地 HMI 失效。
- 云端页面展示的是带时间戳、序列号和质量状态的近实时数据，不能假设数据永远最新。
- Edge 应优先主动连接云端，避免在工厂网络中直接开放公网入站端口。
- 云端远程控制第一版应默认关闭或只读，经过风险评估后再逐步开放。
- 前端按钮禁用不能代替服务端权限校验、参数校验和 PLC 安全互锁。

## 3. 从零开始的实施路线

### 3.1 第一阶段：跑通一条可信的真实链路

第一阶段不要急于搭建复杂平台，应先使用一台设备或模拟器打通完整链路：

```text
PLC/设备模拟器
→ Edge 协议适配
→ 统一设备数据模型
→ MQTT over TLS
→ 云端数据接收
→ 时序数据库
→ WebSocket/API
→ Vue Web HMI
```

统一后的遥测数据至少应包含：

```json
{
  "tenantId": "customer-a",
  "deviceId": "machine-001",
  "tag": "motor.speed",
  "value": 1250,
  "timestamp": 1787356800000,
  "quality": "good",
  "sequence": 10231
}
```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `tenantId` | 标识数据所属客户，实现租户隔离 |
| `deviceId` | 标识设备实例 |
| `tag` | 标识具体测点或业务变量 |
| `value` | 测点值 |
| `timestamp` | 数据在设备或 Edge 侧产生的时间 |
| `quality` | 标识正常、异常、未知或过期等质量状态 |
| `sequence` | 辅助识别乱序、重复和丢失 |

第一阶段的验收条件不只是“页面数字会变化”，还应包括：

- 断网后 Edge 可以缓存数据。
- 网络恢复后能够补传，并正确处理重复和乱序数据。
- 页面能够区分正常、断线、过期和质量异常。
- Edge、云服务或数据库重启后，系统可以恢复。
- 能够从设备到页面追踪一条数据的完整处理链路。
- 时间戳来源和设备、Edge、云端的时钟同步机制明确。

### 3.2 第二阶段：补齐产品基础能力

真实链路稳定后，再逐步增加以下能力：

- 多租户隔离，确保不同客户的数据和操作完全隔离。
- 用户登录、RBAC 权限、密码策略和单点登录。
- 设备注册、设备身份、证书签发、轮换和吊销。
- 报警产生、确认、恢复、复位和审计闭环。
- 历史趋势、数据降采样和数据保留策略。
- 操作日志、设备日志、指标监控和链路追踪。
- Edge 配置版本、软件升级、灰度发布和回滚。
- 数据库备份、恢复演练以及灾备目标。
- API 限流、WAF、密钥管理和漏洞扫描。
- 设备、Edge、云端和 Web HMI 的版本兼容矩阵。

### 3.3 第三阶段：谨慎增加远程控制

远程控制不能只通过 WebSocket 发送一条消息。完整命令链路应包含：

```text
用户发起命令
→ 身份、权限和必要的二次认证
→ 参数范围及设备状态校验
→ 生成 commandId、幂等键和有效期
→ Edge 接收并再次校验
→ PLC 执行互锁和安全判断
→ accepted / executing / succeeded / rejected / timeout
→ 通过设备遥测确认最终状态
→ 全过程写入不可抵赖的审计记录
```

启动、运动、复位等高风险操作可根据风险增加：

- 二次确认或二次认证。
- 双人审批。
- 命令短有效期和防重放机制。
- 仅允许现场局域网执行。
- 维护模式或现场钥匙开关授权。
- PLC 侧最终互锁与拒绝权。

## 4. 当前 Web HMI 项目的演进方向

当前项目主要是 Vue 3 + Vite 前端原型，使用模拟数据验证界面、交互和状态模型。它可以继续作为 Web HMI 基础，但不能仅部署 `dist` 就称为完整云平台。

建议按以下顺序演进：

1. 保留现有页面、Canvas 和领域规则。
2. 将模拟数据源抽象为稳定的 `MachineDataSource` 接口。
3. 增加 REST 和 WebSocket 数据适配器。
4. 引入 TypeScript、Vue Router 和 Pinia，明确页面、状态和通信边界。
5. 增加登录、权限、断线、数据质量和数据过期状态。
6. 建立独立的 Edge 工程和云端后端工程。
7. 设备原始协议由 Edge 解析，Vue 组件只消费统一业务模型。
8. 使用 Docker Compose 建立可复现的本地联调环境。
9. 补充契约测试、端到端测试、断网测试和长时间运行测试。

## 5. 初期技术选型参考

技术选型应优先结合总部平台、团队技能和客户私有化要求，以下组合只作为初期参考：

| 能力 | 可选技术 |
| --- | --- |
| Web 前端 | Vue 3、Vite、TypeScript、Pinia、Vue Router |
| 云端后端 | Java/Spring Boot 或 Node.js/NestJS |
| 业务数据库 | PostgreSQL |
| 时序数据 | TimescaleDB 或 InfluxDB |
| 设备消息 | EMQX/MQTT |
| 缓存 | Redis |
| 文件与升级包 | 云对象存储或 MinIO |
| API 网关 | Nginx 或云 API Gateway |
| 本地开发部署 | Docker Compose |
| 大规模生产部署 | 根据规模评估 Kubernetes，不宜过早引入 |
| 指标和可视化 | Prometheus、Grafana |
| 日志 | Loki、OpenSearch 或云日志服务 |

初期可采用模块化单体后端，先划清设备、租户、报警、命令、审计等领域边界。只有团队和业务规模确实需要时，再拆分微服务。

如果客户普遍要求私有化部署，应优先选择标准协议、容器化部署和可替换的基础设施接口，避免核心能力完全依赖某一家云厂商的专有服务。

## 6. qiankun 与微前端

`qiankun` 是微前端框架，解决的是多个前端应用独立开发、部署和组合的问题，不是产品上云的必要条件。

只有符合以下情况时才建议评估：

- 多个前端团队需要独立开发和发布。
- 平台包含多个边界清晰的独立子产品。
- 不同子应用使用不同前端技术栈。
- 主平台需要按客户或权限动态装载应用。

当前阶段更适合先通过 Vue Router、业务模块和组件库完成模块化。过早使用微前端会增加登录共享、路由协调、样式隔离、公共依赖、通信和版本管理成本。

## 7. 中国大陆上线备案与合规

以下内容是项目规划检查项，具体适用范围应由公司法务、安全团队、云厂商备案顾问及专业测评机构根据业务模式确认。

### 7.1 域名与 ICP

- 使用中国大陆服务器并通过域名向公网提供服务，通常需要进行域名实名认证和 ICP 备案。
- 域名主体信息应与备案主体保持一致。
- ICP 备案通常通过阿里云、腾讯云、华为云等接入服务商提交。
- 网站上线后应按要求在页面底部展示备案号并链接工信部备案系统。
- 收费经营、在线交易或在线数据处理等业务是否需要 ICP 许可证或 EDI 许可证，应根据具体商业模式由专业人员判断。

### 7.2 公安联网备案

网站正式开通后，应根据所在地要求，在规定期限内通过公安机关网络安全服务平台办理联网备案，并按要求展示备案信息。

### 7.3 网络安全等级保护

- 在架构设计阶段开展系统边界识别和等保定级评估。
- 工业云平台通常至少需要认真评估第二级。
- 涉及重要生产控制、较大影响范围或重要数据的系统可能达到第三级。
- 定级、备案、建设整改、等级测评和持续检查应由安全团队及专业机构推进。
- 不应等到系统开发完成后才补做等保，否则可能产生大量架构返工。

### 7.4 隐私和数据合规

- 建立隐私政策、账号注销和个人信息权利响应机制。
- 采用最小必要原则收集个人信息。
- 对个人信息、敏感个人信息、普通设备数据和重要工业数据进行分类分级。
- 明确数据保存期限、访问权限、脱敏、删除和审计策略。
- 对生产数据、日志和备份采用传输加密与存储保护。
- 发布移动 App、小程序或使用受监管算法服务时，另行检查 App 备案、算法备案等要求。
- 政府、央国企或特定行业客户可能提出商用密码、国密算法或行业规范要求，应逐项目确认。

### 7.5 数据跨境

如果中国区的账号、日志、设备信息或工业数据需要传给境外总部，应在实施前完成：

1. 数据清单和数据流向梳理。
2. 个人信息、敏感个人信息和重要数据识别。
3. 数据出境必要性及最小化评估。
4. 境内外访问权限、日志和安全责任划分。
5. 根据数据类型和规模判断是否需要标准合同、认证或安全评估。

不能默认境外总部可以直接访问中国区生产数据库。使用香港或境外服务器通常不需要中国大陆 ICP 备案，但访问质量、网络稳定性和数据跨境合规问题不会因此自动消失。

### 7.6 欧盟业务补充

如果同一产品还面向欧盟市场，应另外评估 GDPR、欧盟《网络韧性法案》（CRA）以及客户行业规范。CRA 的漏洞和重大安全事件报告义务将从 2026 年 9 月 11 日适用，主要合规义务从 2027 年 12 月 11 日适用。

## 8. 十二周试点计划

| 时间 | 主要工作 | 交付物 |
| --- | --- | --- |
| 第 1～2 周 | 确认产品边界、部署模式、协议、数据规模和安全边界 | 上云需求说明、总体架构图、风险清单 |
| 第 3～4 周 | 建立 Edge 接入和标准设备数据模型 | 一台真实设备或模拟器稳定接入 |
| 第 5～6 周 | 建设 MQTT、云端接收、时序存储和实时页面 | 设备到云端页面的完整数据链路 |
| 第 7～8 周 | 建设租户、账号、权限、设备注册和审计 | 可验证的租户隔离和权限模型 |
| 第 9～10 周 | 建设缓存补传、监控、备份、升级和回滚 | 运维手册及异常演练记录 |
| 第 11 周 | 进行压力、断网、重启、重复数据和越权测试 | 测试报告与问题清单 |
| 第 12 周 | 完成试点验收并启动合规准备 | 试点验收报告、ICP/等保/数据合规计划 |

十二周目标是形成一套可信的试点版本和工程基线，不代表已经达到完整商用工业云的成熟度。

## 10. 最重要的三个决策

正式开始前，必须优先得到以下三个问题的明确答案：

1. **云端是否允许向设备下发控制命令？**
2. **产品以公有云 SaaS、客户私有化还是混合部署为主？**
3. **中国区的数据是否需要由境外总部访问或处理？**

这三个决策会直接影响网络拓扑、身份权限、安全等级、数据存储、部署方式和备案合规方案。它们没有明确之前，不应急于引入 qiankun、Kubernetes 或大规模微服务。
